callosum

Callosum records every model request it routes — backend, status, token counts and quota meters before and after — in a local SQLite log.

Repository on GitHub

The problem

You run more than one model backend. A local model for work that must not leave the machine, a hosted one for work that needs more capability, a cheaper one for bulk work. Now every call needs a decision: which one answers this?

In practice that decision does not live in one place. It lives in whichever tool you happened to be in, encoded as a different base URL, a different model name, a different flag. Every caller decides differently, the decision is invisible afterwards, and nobody can answer the question that matters a month later: which backend actually answered, and what it cost.

There are routing products, and they are good. LiteLLM (https://www.getmaxim.ai/articles/top-5-open-source-ai-gateways-for-self-hosted-llm-deployments), Portkey (https://www.ayautomate.com/blog/open-source-llm-orchestration-tools), OpenRouter (https://openrouter.ai), Bifrost (https://www.getmaxim.ai/articles/top-5-llm-gateways-with-an-openai-compatible-api-in-2026), the MLflow AI Gateway (https://mlflow.org/litellm-alternative), Routerly (https://github.com/Inebrio/Routerly), LLMRouter (https://github.com/ulab-uiuc/LLMRouter), RouteLLM (https://github.com/lm-sys/routellm), Relay (https://news.ycombinator.com/item?id=49800187), LunarGate (https://news.ycombinator.com/item?id=47426651), Any-LLM (https://news.ycombinator.com/item?id=44650567), cascadeflow (https://cascadeflow.ai/vs/model-routers), agentgateway (https://agentgateway.dev/blog/2026-02-09-getting-started-agentgateway-llm-routing) and Kong (https://developer.konghq.com/cookbooks/basic-llm-routing) all route requests to a model backend, and several of them have already claimed the local ground. Routerly's own description says: "LiteLLM is self-hosted but requires standing up and maintaining a database just to run. Routerly is self-hosted, zero-dependency, and your data never leaves your machine." (https://github.com/Inebrio/Routerly).

So the routing is not the difference; it is the commodity. The defensible difference is the record: a per-attempt log of what was sent, where it went, what came back, what it cost in tokens, and what the quota meters read before and after, plus per-model latency estimates so the choice can be argued with afterwards. A hosted, multi-tenant gateway does not give you that for one person on one machine, and neither does a router that only decides and forgets.

cares

  • People running local models on their own hardware. They gather in r/LocalLLaMA, in the local language model communities on Hacker News and Lobsters, and in the selfhosted communities.
  • Operators who want one OpenAI-compatible endpoint in front of heterogeneous backends so that the tools they already use — the OpenAI software development kits, curl, editor assistants — keep working unchanged. They gather on Hacker News and in the command-line and selfhosted subreddits.
  • People who care about the record. Anyone who has wondered what the week's requests actually consumed, and which endpoint served them. This is the group the project is built for; the routing is the mechanism that produces the record.
  • Selfhosted-first operators who will not put a key in a hosted router because a hosted router is somebody else's account and somebody else's database. They gather in r/selfhosted and r/commandline.

Model routing is a crowded category, and it is worth being blunt about that: LiteLLM (https://www.getmaxim.ai/articles/top-5-open-source-ai-gateways-for-self-hosted-llm-deployments), Portkey (https://www.ayautomate.com/blog/open-source-llm-orchestration-tools), OpenRouter (https://openrouter.ai), Bifrost (https://www.getmaxim.ai/articles/top-5-llm-gateways-with-an-openai-compatible-api-in-2026), the MLflow AI Gateway (https://mlflow.org/litellm-alternative), Routerly (https://github.com/Inebrio/Routerly), LLMRouter (https://github.com/ulab-uiuc/LLMRouter), RouteLLM (https://github.com/lm-sys/routellm), Relay (https://news.ycombinator.com/item?id=49800187), LunarGate (https://news.ycombinator.com/item?id=47426651), Any-LLM (https://news.ycombinator.com/item?id=44650567), cascadeflow (https://cascadeflow.ai/vs/model-routers), agentgateway (https://agentgateway.dev/blog/2026-02-09-getting-started-agentgateway-llm-routing) and Kong (https://developer.konghq.com/cookbooks/basic-llm-routing) all route requests, and two competitors have already claimed the "self-hosted, zero-dependency, your data never leaves your machine" ground. The framing that reaches a real audience is the narrow one — a single operator, one machine, no account, no key leaving the box, and a log on disk that says what each attempt cost. The broad framing, "a smarter router for everyone", reaches nobody new.

t it does

Callosum is a local, adaptive HTTP routing layer for OpenAI-compatible model backends. It accepts /v1/responses and /v1/chat/completions requests, chooses the best available backend for each request, and forwards the call transparently. Any OpenAI-compatible client can point at it, by setting a base URL and a bearer token.

For each request the routing pipeline:

  1. Drops backends that do not advertise the requested model.
  2. Drops unavailable backends and backends in cooldown.
  3. Drops backends whose quota is exhausted.
  4. Ranks the remaining candidates by predicted cost and quality.
  5. Selects the best available backend and retries on retryable failures.

If no backend can serve the request, the response is a self-diagnosing error that carries cooldown, quota and recovery information.

Clients can use concrete model identifiers, or the virtual model names auto and auto-learning to reach the adaptive router. Selector identifiers are also available, such as callosum:local-only, callosum:remote-only, and callosum:remote/model-id::high, where :: is the explicit reasoning-effort delimiter. Reasoning effort is passed through unchanged when the upstream supports it.

Backends are configured in a single TOML file. Public builds support the codex_gateway backend type. Three backends register themselves when their condition is met rather than through configuration: a local lane, registered when the local-llm command-line tool is available; Ollama Cloud, registered when CALLOSUM_OLLAMA_CLOUD_ENABLED=1; and OpenRouter, registered when CALLOSUM_OPENROUTER_ENABLED=1.

The request log is a SQLite database. When a usage log path is configured, each backend attempt is recorded, and the useful columns are backend_id, model, reasoning_effort, status, classification, prompt_tokens, completion_tokens, total_tokens, five_hourly_used_percent_before, five_hourly_used_percent_after, weekly_used_percent_before and weekly_used_percent_after. With capture_bodies set to true, the compressed request and response payloads are stored as well. It is a record of what was sent, where it went, and what came back — not a full analytics product.

The operator surface is small: GET /status for the backend pool, cooldowns, pin state and session bindings; POST /control/pin and POST /control/unpin to force or release routing to one backend; GET /diagnose/upstream for an upstream health check that inspects HTTP status, quota headers, the Responses API terminal event and the usage block; GET /v1/usage for an empirical per-model, per-reasoning-effort quota rate table with five-hourly and weekly meters reported independently; and POST /v1/eta for approximate pre-flight latency ranges per compatible cell. A session can be pinned to a backend by sending the X-Codex-Session-Id header, though those bindings are process-local and do not survive restarts.

t it does not do

This list is the point of the project, so it goes in the post as well.

  • It is not a hosted gateway. It binds to 127.0.0.1 and is meant to stay there unless you add transport security and authentication yourself.
  • It is not a multi-tenant service. The public README says so directly, and the configuration ships one authentication database with users, sessions and API keys for a single operator, not a customer model.
  • It is not a company cost-control product. It does not do budgets, chargeback, invoicing or per-team metering.
  • It does not bypass provider authentication or quota enforcement. It is a routing proxy, and it says so in its terms of service.
  • It does not guarantee the best model for a task. It ranks candidates by predicted cost and quality against the backends you configured, and the prediction is a prediction.
  • It does not replace your provider accounts. You still hold the keys, and the upstream quotas still apply to you.

of artifact to capture

The request log table. One terminal view showing recent requests with the backend that served each one, the model, the reasoning effort, the status, the token counts, and the five-hourly and weekly usage percentages before and after. That table is the argument: it turns "the machine chose" into a record you can read.

The second artifact, worth having ready, is the GET /status output showing the backend pool with cooldowns and pin state next to a single line from the request log naming the backend that answered.

tall, in one line

uv sync && uv run python -m callosum

Before the first run, create ~/.config/callosum/config.toml with a server block, a state directory, and at least one [[backends]] entry, then check the server with curl -s http://127.0.0.1:8765/health.

three hardest questions

"There is already an open source gateway that does routing. What does this add?" There are several, among them LiteLLM (https://www.getmaxim.ai/articles/top-5-open-source-ai-gateways-for-self-hosted-llm-deployments) and Routerly (https://github.com/Inebrio/Routerly). The public README positions Callosum around a specific case: one operator, one machine, a local model and a hosted model both available. Where a general gateway assumes many clients and many credentials, this is one local process with one configuration file, one local authentication database, and a local request log that records the choice on disk. It is also worth being direct that routing quality is the same open problem for everyone; the difference is the surface area you have to adopt.

"How do I know the router picked well?" You do not get that from a marketing claim, you get it from the log. The request log records, per attempt, the backend, the model, the reasoning effort, the status, the classification, token counts and the quota percentages before and after. GET /v1/usage reports empirical per-model, per-reasoning-effort rates with five-hourly and weekly meters kept separate, and POST /v1/eta gives approximate pre-flight latency ranges per compatible cell, returning available: false when there is not enough data rather than guessing.

"What happens when it picks wrong, or when the upstream is broken?" Backends that are unavailable, in cooldown, or out of quota are dropped before selection. Retryable failures are retried on the selected backend. If no backend can serve the request, the error is self-diagnosing and carries cooldown, quota and recovery information. For an operator who needs certainty rather than adaptation, POST /control/pin forces all routing to one backend and POST /control/unpin releases it.

Two operational notes from the public documentation are worth repeating rather than hiding: use one worker, because the SQLite databases are not safe across multiple workers; and capture_bodies = true stores sensitive prompt and response data, so the request log should be treated as sensitive and archived by hand.
