atelier

atelier keeps provider credentials in a password store and hands tools stand-ins instead.

Repository on GitHub

The problem

Any tool that calls a hosted model provider needs that provider's credential. The credential then ends up in the tool's environment, in its configuration file, in shell history, in the process table, and in every error handler that dumps the environment. This is true of small scripts and true of agents that run unattended for hours.

The usual answers assume the tool and the person are one trust domain. They are not. The tool is a program that runs without supervision; the person is the one whose credential it is. A client that can read its own credential can also log it, ship it in a crash report, pass it to a subprocess, and write it to a log line nobody read for six months.

The second problem is subtler and it is the one that shapes the project. If the operator can read every credential, then the operator is another holder of the secret, and so is every place the operator might paste it. Making the operator unable to read credentials back removes an entire class of exposure, at the cost of a strange administrative model: you can replace a credential but you cannot look at it.

cares

The category is already populated. Four projects broker credentials for agents and have been announced to the same audience:

  • Infisical Agent Vault (https://github.com/Infisical/agent-vault) — "A HTTP credential proxy and vault for AI agents like Claude Code, OpenClaw, Hermes, custom agents + harnesses, and more"
  • AgentSecrets (https://news.ycombinator.com/item?id=47167691) — "Zero-Knowledge Credential Proxy for AI Agents"
  • Authsome (https://news.ycombinator.com/item?id=47936190) — "open-source local auth proxy for AI agents"
  • MCP-warden (https://news.ycombinator.com/item?id=50241410) — "local credential broker so AI agents never see your secrets"

What the scan did not find in any of them is atelier's specific boundary: the operator cannot read a credential back, the store is a password store held by a dedicated service identity with its own key, and there is no control plane to run.

  • People running local tooling against hosted model providers who have thought about where the key sits and did not like the answer. They gather on Hacker News, on r/LocalLLaMA, and in the Python and agent-tooling communities on Dev.to.
  • Operators who rotate credentials and would rather not handle rotated material by hand, and who would rather their tooling never held the original. They gather on Lobsters and in infrastructure forums.
  • Security-minded developers and platform engineers who enjoy an unusual isolation boundary and want to argue about whether it is the right one. They gather on Hacker News, on Lobsters, and on r/cybersecurity.
  • Maintainers of local-first and self-hosted tools who want a credential boundary they can ship without running a control plane. They gather on r/selfhosted and in the password-store and secrets-management communities.

t it does

  • Stores durable provider credentials — OAuth refresh tokens, token bundles, revocable provider API keys and, where a provider exposes usage only through a browser session, a copy of the browser's session cookies — encrypted in a pass password store.
  • Runs as a dedicated system user, atelier, with its own GPG key and its own password store, so that only the atelier service process holds the decryption capability.
  • Refreshes provider credentials when an access token is stale and writes the rotated refresh material back into the store.
  • Mints local stand-in tokens carrying a token identifier, an audience, a scope, an account, issue and expiry times, and a revocation state. The token secret is shown once to the trusted local client; only a hash is stored.
  • Validates the audience, scope, expiry and revocation of a stand-in token on every request, with least-privilege scopes that keep upstream proxying and usage reading apart.
  • Injects the provider credential only inside the final upstream HTTP request, and never returns a provider access token, a provider API key, a refresh token, the full authentication JSON or a decrypted store entry to a client.
  • Gives the operator write-only commands — atelier load put, rm, mv and cp — delegating to a restricted wrapper that permits insertion, removal, moving and copying and never show or edit.
  • Ships a documented integration contract, an architecture document with diagrams, and decision records for the password-store choice and for the operator-isolated custody decision.

t it does not do

  • It is not a general secrets platform, a model router, a prompt transformer or an agent launcher. The project's own status section says exactly this.
  • The operator cannot read a credential back. The operator can write, delete, move and copy, and that is the whole administrative surface.
  • Client tools cannot decrypt anything. They receive a stand-in token, which is local-only, scoped, short-lived and revocable.
  • It does not own model selection, prompt routing, payload transformation, provider account login or client process launch. Those belong to the client.
  • It does not custody a provider's own command line sign-in credentials. Where it holds a copy of browser session cookies, the browser still owns them, the copy is session-scoped with no refresh flow, and rotation is an operator-run re-extraction.
  • It does not have a refresh flow for provider API keys. Rotation is the operator replacing the store entry, and the key is reloaded on the next request.
  • It is an early implementation with a narrow public surface, and it depends on a password store, a dedicated service identity with a GPG key, a restricted sudoers rule and a service installation step. That operational cost is the price of the isolation boundary, and it should be stated rather than hidden.
  • It does not store credentials for you. You load them.

tall, in one line

sudo deploy/systemd/install.sh && sudo systemctl enable --now atelier.service

That builds the package as a wheel, creates a virtual environment for the atelier service user, renders the systemd unit, and starts the service. Verify it with:

curl -fsS http://127.0.0.1:7342/health

The password store, the GPG key for the service user, the restricted wrapper and the sudoers rule are prerequisites, documented alongside the installer.

three hardest questions

"If the operator cannot read the credential, how do they know it is correct, and how do they rotate it?" Rotation is by replacement, not by inspection. The operator writes the new material over the old entry with atelier load put, deletes it with atelier load rm, and moves or copies it with mv and cp. For OAuth bundles, the service itself refreshes the access token and writes the rotated refresh material back into the store, so the operator never handles it. For provider API keys there is no refresh flow at all, by design: the key is revocable, non-expiring, and rotation is the operator replacing the entry, after which the key is reloaded on the next request. The honest cost of this model is that you cannot eyeball what you have configured, and that is a real price, not a rhetorical flourish.

"Isn't this just a secrets manager with extra steps? Why not use the one you already run?" The credential-proxy category is already occupied, and the four closest projects say so themselves:

  • Infisical Agent Vault (https://github.com/Infisical/agent-vault) — "A HTTP credential proxy and vault for AI agents like Claude Code, OpenClaw, Hermes, custom agents + harnesses, and more"
  • AgentSecrets (https://news.ycombinator.com/item?id=47167691) — "Zero-Knowledge Credential Proxy for AI Agents"
  • Authsome (https://news.ycombinator.com/item?id=47936190) — "open-source local auth proxy for AI agents"
  • MCP-warden (https://news.ycombinator.com/item?id=50241410) — "local credential broker so AI agents never see your secrets"

None of those four has the boundary atelier has. The difference is three things: the operator cannot read a credential back, the store is a password store held by a dedicated service identity with its own key, and there is no control plane to run.

Beyond that, by its own status section, atelier is not a secrets platform and does not try to be one. A hosted secrets manager still has to hand the credential to the workload, and the workload then holds it in memory, in the environment, and in whatever it writes to a log. atelier gives the client a stand-in token that is not valid at the provider, and the real credential is injected only inside the final upstream request. The other difference is the direction of the trust boundary: it deliberately takes away the operator's ability to read the secret back, which most tools will not do.

"How do I know the proxy is not itself logging or leaking the credential?" Read the implementation, and the integration contract says in advance what is forbidden. atelier must not return a provider access token, a provider API key, a refresh token, the full authentication JSON or decrypted store contents to any client. Stand-in token secrets are shown once and only a hash is stored. There are explicit redaction and non-disclosure rules for credential-bearing errors, and the scopes are least-privilege and distinct, so a client that only reads usage meters does not hold the upstream-proxying scope and a proxy client does not implicitly gain usage reading. The dependency worth naming is that the isolation depends on the store being decryptable only by the service user's GPG key; if that key is readable by the operator, the boundary is gone.
