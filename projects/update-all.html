update-all

update-all updates your workstation by default and only reports the risky updates until you ask.

Repository on GitHub

The problem

Updating a workstation is three different jobs wearing one hat.

Package-manager upgrades are routine. Firmware updates and runtime bumps are risky and want a human present. Global tool upgrades sit in between and are frequently the thing that breaks a working setup.

Most updaters present all of these as one action behind one switch, so the choice is between running everything with a flag you did not understand and running nothing at all. Neither is a policy.

The second problem is coverage. Nobody can say, without running something, what on the machine is actually updatable. A tool that updates four package managers and says nothing about the rest of the machine reads like a tool that covers the machine.

One command that updates everything is not the novel part, and the pitch should not claim it. RepoRover already advertises "update all your Linux package managers in one place" (https://www.youtube.com/shorts/lh-092vOG6Q), and Topgrade "automatically discovers what package managers, language toolchains, and tools are installed and runs the appropriate update command for each" (https://rustutils.com/tools/topgrade). The ground this project occupies is narrower: which updates are applied without a human present, which are only reported, and where the coverage stops.

cares

  • Operators who keep several machines in a known state and want the routine part to be genuinely routine. The question they ask is asked in public, on Ask Ubuntu (https://askubuntu.com/questions/733434/one-single-command-to-update-everything-in-ubuntu), on the Linux Mint forums (https://forums.linuxmint.com/viewtopic.php?t=423991), on Superuser (https://superuser.com/questions/31096/what-linux-distribution-has-the-most-up-to-date-packages) and in the Apple forums (https://discussions.apple.com/thread/253125686).
  • People who have been broken by an unattended runtime upgrade and now want a tool that refuses to do that by default. They gather in the same question threads, and in Hacker News threads about update policy.
  • People who want to know what they are missing. The inventory mode is for the operator who cannot answer "what is out of date on this box" without guessing.
  • Makers of unattended and workstation images who need a non-interactive command with a machine-readable exit status. They gather in r/devops, in the source distribution and container communities, and on Hacker News.

t it does

update-all is an operating-system-agnostic workstation update orchestrator. Safe package-manager updates run by default. Firmware, runtime bumps and global pip upgrades are reported without changing the machine unless their flags are supplied. There is no single flag that means "update everything": each lane flag opts its own lane into apply mode.

The supported paths are Linux — Debian and Ubuntu, Fedora and RHEL, Arch, openSUSE, Alpine, Void and Gentoo — plus macOS, and detection-only Windows shells, with Windows itself deferred. Cross-cutting managers are used only when they are present.

Topgrade is the primary driver when it is installed and healthy. The maintained Bash-native dispatch is a complete first-class fallback covering the same manager families, so no optional dependency is load-bearing: if Topgrade disappears or becomes unmaintained, the fallback still works.

The manager families the inventory audit knows about are apt, dnf, pacman, zypper, apk, xbps, brew, mas, snap, flatpak, pipx, npm, cargo, mise, mise-self, uv-tool, uv-python, uv-self and pip.

Three modes matter to an operator:

  • --dry-run previews the exact commands.
  • --inventory prints a coverage audit of discovered software channels and executables before updating; --inventory-only runs that audit and exits without changing the machine.
  • --inventory-json prints the same audit as machine-readable JSON to stdout and exits, or with a path it writes the snapshot atomically, rotates the prior snapshot, keeps a change-detection index, and prints a summary diffing the current snapshot against the last run. The export is pure Bash, never executes an arbitrary swept binary, and does not depend on a Python interpreter.

Inventory entries are classified as apply (this command updates them), report (this command can only inspect or flag them) or manual (no trustworthy automated updater is wired in yet). The classification is honest about ownership: a pipx virtual-environment shim is owned by pipx, a uv tool shim by uv, a standalone uv binary by uv itself, a mise shim by mise, a cargo-installed tool by cargo — cargo upgrades are reported and never applied, because cargo has no first-party per-crate updater — and a symlink into a git working tree is developer tooling tracked by its repository, not a manual update gap.

The trusted set of self-updating AI command-line tools is a small registry in the script, currently Codex, Claude, Hermes and Goose; adding a future one is one registry line. Tools not in the registry are never auto-run or auto-updated, and the inventory flags names that look like these tools as manual gaps so the operator can decide.

Every manager is isolated: one failure is reported and does not abort later steps. The command ends with a loud reboot and restart status summary, and the exit status is a stable contract — 0 for complete, 1 for an incomplete run with a failed apply step, 2 for invalid arguments, 3 for privilege required but unobtainable. The end-of-run summary also prints machine-greppable lines such as apply failures=N report failures=N (total=N) and either RESULT: update complete or RESULT: update incomplete. It is non-interactive by design, so it can be driven from an external orchestrator or a CI runner.

Root-tier steps — native package managers, snap refresh, firmware — escalate through sudo; user-tier steps run as the invoking user, so nothing installs into the wrong home directory. No systemd timer is installed; operation is manual by design.

t it does not do

  • It does not update everything by default. Firmware, mise runtime upgrades, mise self-update, uv tool upgrades, uv Python upgrades, uv self-update, the trusted AI command-line tools, and global pip are reported only unless their flags are supplied. Global pip updates are always report-only.
  • --full does not mean "everything". It widens only the distribution's native upgrade mode, for example apt dist-upgrade instead of apt upgrade. It does not apply any other lane; flags are combined to include them.
  • It does not update cargo-installed tools. Cargo owns them, and there is no first-party per-crate updater that is trusted by default.
  • It does not guess update commands for unknown binaries. A name that looks like an AI command-line tool but is not in the registry is surfaced as a manual gap, not acted on.
  • It does not update every GUI application, AppImage, vendor installer or standalone binary in a directory. Package-manager coverage does not imply that, and the inventory mode exists to make the gap loud.
  • It does not manage operating system upgrades as such, and it does not install software you did not ask about.
  • Windows is detection only and deferred.
  • It does not install a timer or schedule anything.

of artifact to capture

The --inventory-json output on a real machine, rendered as a table: one row per discovered channel and executable, each classified apply, report or manual, with the note explaining why. Beside it, the == summary == block and the RESULT: line.

That pairing is the argument. The first artifact shows what the tool can and cannot cover, including the gaps; the second shows the exit-status contract that lets a caller act on the result without parsing prose.

tall, in one line

git clone https://github.com/rohankhanna/update-all.git && cd update-all && ./update-all --dry-run

The dry run is also the best demonstration of the design, because it shows the exact boundary between the safe default and the guarded operations.

three hardest questions

"Why not just use Topgrade?" Because Topgrade is genuinely good at the thing its name suggests. It "automatically discovers what package managers, language toolchains, and tools are installed and runs the appropriate update command for each" (https://rustutils.com/tools/topgrade), and that source lists cargo, rustup, go, composer, conda, npm, gem and pip among its systems. Several of those are lanes this tool reports rather than applies — cargo, because cargo has no first-party per-crate updater, and global pip, which is always report-only — so the coverage argument does not hold. This tool uses Topgrade as its primary driver when it is installed and healthy.

The difference is the split between applying and reporting, and the inventory audit. The default run applies only safe native package-manager upgrades and reports every other lane; each lane flag opts its own lane into apply mode, and there is no flag that means "update everything". --inventory then prints every discovered software channel and executable and classifies it as apply, report or manual, gaps included, so the coverage claim is checkable instead of asserted.

"What happens when Topgrade goes away, or when it breaks?" Nothing essential stops working. The Bash-native dispatch is the permanent survival implementation, not a degraded stub, and it is kept in sync as supported managers and safety rules evolve. It covers the same manager families. No optional dependency is load-bearing.

"Does it need root, and what happens if it cannot get it?" Root-tier steps — native package managers, snap refresh, firmware — escalate through sudo, and the password prompt is the only interactive point. User-tier steps always run as the invoking user, even when the script itself is run under sudo, so nothing installs into the wrong home directory. If sudo is unavailable and the script is not root, it prints a clear message and exits with status 3, which is deliberately distinct from status 1 so a caller can retry with elevation instead of treating it as a review-required failure.
