prior_art

Install a required research step into a repository, and fail when the evidence is missing.

Repository on GitHub

The problem

Before an assistant writes anything in a repository, the most valuable question is whether something already does this and should be used instead of built. In practice that question gets skipped, because skipping it is free and asking it costs minutes. The bill for skipping it arrives later, as a rewrite.

A repository that wants the question asked every time needs a rule that survives the session, lives with the code, and cannot be quietly ignored. That means a file in the repository, checked by something, not a habit and not a setting in a tool that may be turned off.

cares

Two projects sit close to it, and a reader will meet them first.

  • The lead project on the GitHub topic page for prior art search is described as "Prior-art exploration for your own software project: MCP server + Agent Skill that find related patents and report observations, never a verdict" (https://github.com/topics/prior-art-search). The findings do not give that project's own name or repository address, so its name could not be confirmed.
  • five0nit/brief2ship — "Search and score local code, GitHub, PyPI, npm, crates.io, and Hugging Face before building—then ship with proof" (https://github.com/topics/repository-discovery).

Both are model-prompted skills: the research step is a prompt the model may follow, per session, and nothing checks that it happened. This project is a requirement installed in the repository, with a fail-closed checker and dated evidence.

  • Maintainers who work with assistants heavily and have already paid for a rebuild that an existing tool could have covered. They gather on Hacker News, in r/ExperiencedDevs, and in r/programming.
  • People who have watched an assistant confidently reinvent something that already existed.
  • Teams that tried to enforce this by convention and watched the convention erode within a month.
  • Anyone who wants the question asked at the point where it is cheapest to answer, which is before the change is written rather than after.

t it does

prior_art is a single command-line tool. One install step places it on the path; from there the apply and check subcommands operate on the current directory by default, or on an absolute repository path.

  • It installs a required research step into the repository's agent instruction file, AGENTS.md, and keeps CLAUDE.md, GEMINI.md and HERMES.md as exact replicas of it.
  • The installed section requires, before substantive work, that a daily research gate is satisfied.
  • The gate has two levels: a product-level scan asking whether existing tools already satisfy the intent, and a work-slice scan asking whether the specific change in front of the operator is already solved.
  • Evidence is one file per local calendar day, named for that date. A refreshed product scan has to cite at least one external address.
  • Freshness is expressed as a speed class: tectonic, snail, walking, fast, rapid or lightspeed, each with its own interval.
  • Slices are typed: mechanical, which carries the minimal fields, and capability, which carries the full build-versus-buy set and requires differentiation when the action is to build.
  • The posture is written into the contract: prefer adopt, integrate, extend, contribute, narrow the scope, wait, or stop over building.
  • Sensitive material is not allowed in the evidence file; the contract requires redaction instead.
  • The checker is fail-closed. If the evidence for the day is missing or malformed, it refuses rather than passes.
  • apply is idempotent. It creates or refreshes its own section in AGENTS.md without disturbing adjacent sections installed by other tools, installs the gate contract and the checker script into the repository, and regenerates the three mirror files.
  • help prints the usage.

The tool does not perform the research itself. It requires the research and checks that the evidence exists.

t it does not do

  • It does not do the research. It requires it and checks for the evidence.
  • It does not judge the quality of the research. It checks the shape of the evidence: a named scan, a date, a speed class, a typed slice, and an external citation when a scan is refreshed.
  • It does not stop an assistant from ignoring the instruction. It makes ignoring it visible, because the checker fails and the failure is visible.
  • It does not replace judgment on whether to build. It records the decision and the alternatives considered, so the decision is visible later.
  • It does not run a model. It is a shell tool that reads a file and checks its structure.
  • It does not search the internet for you. The external citation in the evidence file is written by the person doing the work.

of artifact to capture

A terminal card showing the checker refusing to pass in a repository where the day's evidence file is missing, with the non-zero exit visible, followed by the same check passing once the evidence file exists. The refusal is the artifact: a checker that only ever succeeds would be a different and much weaker tool.

tall, in one line

git clone https://github.com/rohankhanna/prior_art.git
cd prior_art
./prior-art install

The installer links the command into ~/.local/bin, so that directory has to be on the path. Once installed, the tool has three subcommands: apply, which installs the section, the contract and the checker into the repository you run it from; check, which validates the daily gate for that repository; and help, which prints the usage. Both apply and check also accept an absolute repository path instead of defaulting to the current directory.

three hardest questions

"Isn't the checker just theatre? It verifies the shape of a document, not the quality of the research." Correct, and it is deliberately shaped that way. A checker that tried to judge research quality would either need a large model call on every change or settle for a rule nobody can falsify. This one checks that a named scan happened on a named day, with a speed class that says how fresh it has to be, a typed slice, and at least one external citation when a scan is refreshed. It refuses the file when that is not true. It verifies the record, and it refuses to guess about the judgment.

"This is just a prompt with extra steps. Why does it need a tool?" Because the nearest neighbours are prompts too: the lead project on the prior art search topic page, "MCP server + Agent Skill that find related patents and report observations, never a verdict" (https://github.com/topics/prior-art-search), whose own name the findings do not give, and five0nit/brief2ship, "Search and score local code, GitHub, PyPI, npm, crates.io, and Hugging Face before building—then ship with proof" (https://github.com/topics/repository-discovery). Both are model-prompted skills, so both depend on the model choosing to run them.

Because a prompt lives in a session and a file lives in the repository. The tool's contribution is that the requirement is checked mechanically, on a schedule, by something that cannot be satisfied by asserting that the research was done. The evidence is a dated file with a shape, and the checker fails closed when it is absent.

"Requiring this on every change would slow everything down." On small mechanical changes it would, if the rule had only one level. It has two: the product-level scan can be reused while it is still within the interval its speed class allows, and the work-slice record for a mechanical change carries the minimal fields. So the recurring cost is a freshness decision rather than a full research pass, and the intervals are set by the project rather than fixed by the tool.
